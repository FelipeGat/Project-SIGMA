### Isolamento entre Tenants

Validado com **dois Tenants reais**, criados pelo CLI:

| Requisição | Status obtido |
|---|---|
| Tenant B cria Mission própria | `201` — prova que o token de B é válido |
| **Tenant B lê Mission do Tenant A** | **`404`** |
| Tenant A lê a própria Mission | `200` |

O `201` na primeira linha é o que torna as duas seguintes conclusivas: o `404` vem do isolamento, não de um token inválido. (Uma primeira tentativa desta verificação produziu `401` por erro de parsing do token no script — refeita e corrigida antes de registrar aqui.)

## Architecture Validation

- `services/gateway` importa apenas `Interfaces/` dos Engines (via `Bootstrap`) e casos de uso resolvidos pelo container; `MissionEndpoints` importa Value Objects de `Domain/` para montar entrada e apresentar saída, **nunca** `Infrastructure/` de nenhum Engine.
- Nenhum Engine passou a depender de outro Engine. `packages/mission-engine` continua sem qualquer referência a `identity-engine` — a ponte entre os dois vive no gateway, que é o lugar previsto para isso.
- `composer.lock` do gateway lista `sigma/core`, `sigma/kernel`, `sigma/event-bus`, `sigma/identity-engine`, `sigma/mission-engine` — nada além.
- `system-manifest.yaml`: comentários de `identity-engine`/`mission-engine` atualizados para refletir que o gateway agora os registra.

## Scenario Validation

Cada critério de aceite da Proposal, com o resultado real:

- ✅ **Critério 1 — usuário criado do zero loga, seleciona Workspace, cria e consulta Mission, tudo por HTTP.** Executado contra Docker real; a sequência completa e sua saída estão na seção HTTP acima.
- ✅ **Critério 2 — Mission persistida no MariaDB e evento publicado no Redis.** Consulta direta ao banco confirma a linha em `missions` (`id`, `status=created`, `objective`), e as seis tabelas do Mission Engine (`missions`, `subtasks`, `subtask_retry_attempts`, `approval_gates`, `compensations`, `mission_history`, mais a tabela de controle `mission_engine_migrations`) convivendo com as do Identity Engine no schema `sigma_identity`. `redis-cli psubscribe "mission.*"` capturou, cross-processo, o payload real: `{"missionId":"46d2f9db-...","correlationId":"d0cbb944-...","tenantId":"c855c1a3-...","workspaceId":"198d1d86-...","intentId":null}`.
- ✅ **Critério 3 — `restart: on-failure` ativo e `memory-worker` recuperando sozinho.** `docker compose stop redis` → worker entrou em `Restarting (255)`; `docker compose start redis` → worker de volta a `Up` em **~6s**, log confirmando `memory-worker: pronto, aguardando identity.created/workspace.selected.` O achado de prioridade alta da Release 4.5 está **verificado como resolvido**, não apenas alterado no arquivo.
- ✅ **Critério 4 — suíte completa verde, sem regressão.** 265/265, 0 pulados.
- ✅ **Critério 5 — Decision Log e Validation Report publicados.** Este documento e o [Decision Log](0005.5-vertical-slice-decision-log.md).

## Pendências

Tudo que não foi validado ou ficou em aberto, sem exceção:

1. **`services/auth` não tem endpoint de health nenhum** — nem `/health/live`, nem `ready`, nem `startup`, apesar de [ADR-0042](../adr/0042-health-estilo-kubernetes.md)/[BOOTSTRAP.md](../../BOOTSTRAP.md) os definirem como padrão de todo processo deployável. Seu `public/index.php` responde `503` a toda rota quando o boot falha — correto para rotas de domínio, mas não há liveness a preservar ali porque ela nunca existiu. *(Correção: uma versão anterior deste relatório e do Decision Log descrevia isto como "o mesmo problema do gateway", o que estava errado — o gateway tinha os três endpoints e os perdia no boot falho; o auth nunca os teve.)*
1b. **Nenhum serviço do SIGMA tem `healthcheck` no `docker-compose.yml`** — só `redis` e `mariadb`, que são imagens de terceiros. `gateway` implementa os três endpoints de health desde a Release 2 e **nada os consome**: o `restart: on-failure` adicionado nesta Release reage a processo que morre, não a processo que ficou `not_ready`. Achado desta rodada, fora do escopo aprovado, não corrigido.
2. **`CreateTenant`/`CreateCompany`/`CreateWorkspace` não publicam evento de domínio** — decisão consciente (ver Decision Log); revisitar se/quando `tenant.created` fizer falta a algum consumidor.
3. **Migrations continuam rodando na primeira requisição HTTP** (`boot()`), agora com dois Engines no gateway. Risco 2 da Proposal, aceito conscientemente; pendência aberta desde a 3B.
4. **PHP 8.4 (ADR-0009) não validado** — host roda 8.5.8, containers 8.2.33.
5. **Coverage não medida.**
6. **Redis pub/sub sem replay** — limitação confirmada na 4.5, inalterada. `restart: on-failure` faz o worker voltar, mas **não** recupera as mensagens publicadas durante a queda.
7. **`Identifier` segue duplicada em três pacotes** — não tocada nesta Release.
8. **`GET /missions/{id}` usa `preg_match` no front controller** — funciona para uma rota com segmento variável; não escala para a API completa da Release 12.
9. **Nenhum teste de carga/concorrência sobre as rotas novas** — a 4.5 mediu o `memory-worker`, não o gateway com banco.
10. **Sem paginação ou listagem** — não existe `GET /missions` (coleção), apenas por ID. Não pedido na Proposal.
