# Release 4.5 — Platform Validation — Validation Report

Prova de execução da fase de Validation ([ADR-0048](../adr/0048-processo-quatro-fases.md), [ADR-0056](../adr/0056-validation-report-obrigatorio.md)). Proposta: [0004.5-platform-validation.md](0004.5-platform-validation.md) (revisão 1).

## Release

Release 4.5 — Platform Validation.

## Ambiente

- Windows 10 Pro, XAMPP + Docker Desktop 4.79.0 (Docker Compose v5.1.4).
- Execução: 2026-08-04, ambiente Docker genuinamente limpo (`docker compose down -v` antes de `up`).
- Cinco containers: `redis`, `mariadb`, `gateway`, `auth`, `memory-worker`.

## Os dez itens, cada um com evidência real

### 1. Stress test — 1000 eventos

1000 eventos `identity.created` sintéticos publicados via Redis real (`PUBLISH`), medindo processamento pelo `memory-worker` real contra MariaDB real.

```json
{
  "events_published": 1000,
  "publish_duration_s": 0.14,
  "publish_events_per_sec": 7168,
  "events_processed": 1000,
  "processing_duration_s": 8.928,
  "processing_events_per_sec": 112,
  "events_lost": 0
}
```

✅ **0 eventos perdidos.** Publicação é ~64× mais rápida que o processamento — o gargalo é o processamento sequencial de `RedisSubscriber` (uma mensagem por vez, um handler PHP + uma escrita MariaDB por evento), não capacidade de publicação. Nenhum indício de fila crescendo sem limite ou de o worker cair sob esse volume.

### 2. Restart de containers — recuperação

Cada container reiniciado individualmente (`docker compose restart <serviço>`), em sequência: `auth`, `gateway`, `memory-worker`, `mariadb`, `redis`.

- ✅ `auth`, `gateway`: voltam a `healthy`/respondendo normalmente.
- ✅ `mariadb`, `redis`: voltam a `healthy` (health check do próprio `docker-compose.yml`).
- ❌ **`memory-worker`: NÃO recupera sozinho.** Reiniciado por último na sequência, no momento em que `mariadb`/`redis` ainda estavam no próprio ciclo de restart — o processo caiu com `Predis\Connection\ConnectionException` e ficou `Exited (255)` até um restart manual explícito (`docker compose up -d memory-worker`). **Achado real, não esperado antes desta Release** (ver Decision Log): nenhum serviço do `docker-compose.yml` declara `restart:` policy.

### 3. Perda do Redis — recuperação

`docker compose stop redis`, com `auth`/`memory-worker` já rodando.

- `memory-worker`: morreu imediatamente (mesma causa do item 2 — conexão bloqueada de `pubSubLoop()` derrubada).
- `auth`: continuou de pé. Um `POST /auth/login` real, feito com o Redis parado, retornou `500`/`auth.internal_error` de forma controlada (Envelope completo, nenhum crash) — comportamento já corrigido na Release 3B.
- `docker compose start redis` → `auth` voltou a responder `200` no próximo login **sem nenhum restart** — recuperação automática confirmada.
- `memory-worker` precisou de restart manual (`docker compose up -d memory-worker`) para voltar.

### 4. Perda do Worker — recuperação

Com `memory-worker` já fora do ar (herdado do item 3), um usuário real fez login e selecionou um Workspace **novo** (criado especificamente para este teste, id `d5cfa5e1-...`) via `services/auth` — ambas as chamadas HTTP retornaram `200`.

Depois de religar o `memory-worker`:

```json
{"identityId":"f9927b20-...","userId":"acc3f2db-...","workspaceId":"10669024-..."}
```

❌ **O `UserTwin` continuou mostrando o Workspace anterior (`10669024-...`), nunca o novo (`d5cfa5e1-...`).** O evento publicado durante a queda foi perdido para sempre — Redis pub/sub não persiste para assinante ausente. Esperado desde a Proposal; confirmado com evidência concreta, não apenas em teoria.

### 5. Múltiplos usuários concorrentes

20 usuários (Tenants/Companies/Workspaces isolados, semeados via `RegisterIdentity`) autenticados **simultaneamente** via `curl_multi` contra `POST /auth/login` real, seguido de 20 seleções de Workspace **simultâneas** via `POST /auth/workspace`.

```json
{"users": 20, "login_successes": 20, "login_failures": 0, "workspace_select_failures_or_mismatches": 0}
```

✅ Cruzamento pós-teste, MariaDB real: os 20 `UserTwin`s resultantes têm `workspaceId` exatamente igual ao Workspace do **próprio** usuário — `checked: 20, mismatches: 0`. Nenhuma contaminação cruzada sob concorrência real, mesmo com 20 eventos `workspace.selected` chegando ao mesmo tempo no `RedisSubscriber` de processamento sequencial único.

### 6. Memory Promotion sob dados reais (volume)

200 `MemoryRecord` `Operational` criados via `PdoMemoryRecordRepository` real (MariaDB real) — 20 `subjectKey`s × 5 Workspaces × 2 Missions, metade dos `subjectKey`s com `confidence` alta (0.97, cruza os dois pisos) e metade baixa (0.60, nunca cruza o piso de `Operational→Project`).

```json
{
  "total_operational_records_created": 200,
  "promoted_to_project": 50, "expected_promoted_to_project": 50, "promoted_to_project_matches_expected": true,
  "promoted_to_long_term": 10, "expected_promoted_to_long_term": 10, "promoted_to_long_term_matches_expected": true,
  "elapsed_seconds": 3.276
}
```

✅ Contagem exata em ambos os saltos — os dois gates (estrutura + `confidence`) continuam corretos em volume, não só nos 35 testes unitários já existentes da 4A.

### 7. Twin Sync ampliado

Um usuário, 4 trocas sucessivas de Workspace (cada uma via login+seleção reais, já que `Session::withWorkspaceSelected()` só permite uma seleção por Session — ver Release 3B).

```json
{"state": {"...","workspaceId":"e467176f-9002-432b-a87d-492d3a6ac3a4"}}
```

✅ O `workspaceId` final é exatamente o da **última** troca (`e467176f-...`, a 4ª de 4) — confirma que atualizações em sequência rápida para a mesma identidade sempre convergem para o último evento processado.

### 8. Latência

200 medições sequenciais, uma por vez: tempo entre `PUBLISH` e o `UserTwin` correspondente aparecer na MariaDB.

```json
{"sample": 200, "missing": 0, "p50_ms": 6.03, "p95_ms": 11.86, "p99_ms": 22.82, "min_ms": 5.69, "max_ms": 23.01}
```

✅ Latência de ponta a ponta (Redis → `memory-worker` → MariaDB) consistentemente abaixo de 25ms mesmo no p99, com o worker de pé e sem contenção.

### 9. Event Replay

Verificado diretamente pelo resultado do item 4: **não existe nenhum mecanismo de reprocessar um evento perdido.** `RedisSubscriber` não implementa buffer, fila ou histórico próprio; Redis pub/sub (usado aqui, não Streams) não guarda mensagem para assinante ausente. Confirmado, não implementado nesta Release (ver Decision Log — decisão deliberada).

## Pendências

- **`docker-compose.yml` sem `restart policy` em nenhum serviço** — achado não previsto, prioridade alta para antes de produção real (ver Decision Log).
- **`memory-worker` não sobrevive a nenhuma interrupção de conexão Redis** (restart do Redis, não só timeout de inatividade) — sem retry/reconexão automática.
- **Perda de mensagem durante queda do Worker é definitiva** — sem fila/replay; migrar para Redis Streams é a correção estrutural, não implementada nesta Release (fora de escopo, ver Proposal).
- Throughput de processamento (~112 eventos/s) é single-threaded por natureza (`RedisSubscriber` processa uma mensagem por vez) — se o volume real da Mission Engine exigir mais, paralelização (múltiplas instâncias de `memory-worker`, ou consumer groups do Streams) é uma decisão futura, não avaliada aqui.
