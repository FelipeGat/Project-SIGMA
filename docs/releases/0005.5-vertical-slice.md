# Release 5.5 — Vertical Slice

Proposta formal, no formato exigido por [ADR-0010](../adr/0010-processo-por-epicos-com-aprovacao.md), seguindo o processo de quatro fases de [ADR-0048](../adr/0048-processo-quatro-fases.md). **Revisão 1 — aguardando aprovação do Product Owner.**

Marco de engenharia entre a Release 5 (Mission Engine, completa) e a Release 6 (Planner Engine), no mesmo espírito das Releases 3.5 e 4.5: uma Release fora da numeração principal, para consolidar antes de seguir. Onde a 3.5 auditou coerência entre documentação e código e a 4.5 auditou comportamento sob falha, a **5.5 fecha o primeiro caminho de ponta a ponta do SIGMA** — do login humano até uma Mission criada, persistida e consultável.

## Objetivo

Provar, com uma requisição HTTP real, que as cinco Releases construídas até aqui funcionam **juntas como um sistema**, não apenas como pacotes verdes isoladamente.

Hoje o Mission Engine está completo nas quatro camadas — quinze casos de uso, seis tabelas, treze eventos, 51 testes — e **não existe nenhum caminho para criar uma Mission**: nenhum service registra `MissionEngineModule`, nenhum endpoint o expõe. O mesmo vale, em menor grau, para o Identity Engine: `RegisterIdentity` existe desde a Release 3B e nunca foi exposto, então nem sequer há como criar o primeiro usuário sem `INSERT` manual no MariaDB.

Esta Release remove esses dois bloqueios, e nada além disso.

## Escopo

**Existe** — três entregas, nesta ordem:

1. **`restart policy` no `docker-compose.yml`** — achado de prioridade alta da Release 4.5 ([Validation Report 4.5](0004.5-platform-validation-validation-report.md)), sinalizado e nunca endereçado: nenhum serviço tem política de reinício, e o `memory-worker` não se recupera sozinho de nenhuma interrupção de Redis. `restart: on-failure` nos cinco serviços. Correção pontual, não muda comportamento de domínio.

2. **Bootstrap de Identity via CLI** — `services/auth/bin/bootstrap-identity.php`, seguindo o padrão já estabelecido por `services/memory-worker/bin/worker.php` (binário sem HTTP dentro do service). Cria a hierarquia mínima operável — Tenant → Company → Workspace → User com senha — usando os casos de uso já existentes do Identity Engine, nunca `INSERT` direto. Deliberadamente **CLI e não endpoint HTTP**: um endpoint público de registro é decisão de produto (quem pode se registrar, sob qual convite, com qual verificação) que esta Release não tem contexto para tomar.

3. **Dois endpoints de Mission em `services/gateway`**:

   | Endpoint | Caso de uso já existente |
   |---|---|
   | `POST /missions` | `CreateMission` |
   | `GET /missions/{id}` | `GetMission` |

   Ambos exigem `Authorization: Bearer <sessionToken>` e respondem no Envelope do SIGMA Protocol, como todo endpoint já existente. `POST /missions` recebe o `Plan` no corpo da requisição — o que é **literalmente o que [ADR-0092](../adr/0092-plan-e-conceito-proprio-do-mission-engine.md) determina**: o Plan é entrada do Mission Engine, nunca produzido por ele. `PlanSource::Manual` é o único valor possível enquanto o Planner Engine não existir, exatamente como `Plan.php` já documenta.

**Não existe** — explicitamente fora do escopo:

- **Os outros treze casos de uso do Mission Engine** (`ApproveMission`, `AssignSubtask`, `FailSubtask`, `CompensateSubtask`, …). Criar e consultar bastam para provar o caminho; expor o ciclo de vida inteiro é escopo de uma Release de API própria (Release 12 do ROADMAP).
- **Qualquer Engine novo.** Nenhuma linha de `Domain/` de nenhum Engine muda.
- **Interface gráfica.** `apps/*` continuam vazios. A superfície desta Release é `curl`.
- **Endpoint HTTP de registro de usuário.** Ver item 2 acima.
- **Framework HTTP no gateway.** O front controller `match`-based da Release 2 comporta duas rotas novas; trocar por Laravel continua sendo decisão da Release 12, como o [Decision Log da Release 2](0002-sigma-bootstrap-decision-log.md) definiu.
- **Migrar Redis pub/sub para Streams.** Limitação real confirmada na 4.5, permanece aberta e documentada.

## Arquitetura

`services/gateway` deixa de ser um processo sem estado e passa a registrar dois Modules — `IdentityEngineModule` (para validar a sessão do requisitante) e `MissionEngineModule` (para atender às duas rotas). Ambos apontam para a mesma MariaDB já em uso, em schemas que já existem; nenhum banco ou container novo.

Isso é coerente com o que `services/gateway/README.md` já declara — *"o gateway expõe cada Engine à medida que ele existe, não de uma vez"* — e com [BOOTSTRAP.md](../../BOOTSTRAP.md): o Bootstrap não sabe que "Mission Engine" existe, apenas carrega o que o `system-manifest.yaml` declara como Module. O manifesto ganha os dois Modules no perfil do gateway; nenhuma linha do Kernel muda.

A validação de sessão reusa `AuthenticateSession`/o repositório de Session já implementados na Release 3B — o gateway não reimplementa autenticação, apenas resolve o caso de uso existente pelo container.

## Dependências

- Release 3B (Identity Infrastructure), 4B (Memory Infrastructure), 5C (Mission Infrastructure) — todas completas e validadas.
- Docker Desktop com MariaDB e Redis, já validado nas Releases 4.5/5C.

## Riscos

1. **O gateway ganha dependência de banco pela primeira vez** — até aqui ele subia sem MariaDB, e `/health/ready` passava a depender dela. Mitigação: o `IHealth` já reporta estado por Module com granularidade `degraded`, então uma MariaDB fora do ar degrada os Modules de domínio sem derrubar `/health/live`. Este risco é, na prática, o primeiro teste real do `degraded` granular desenhado na Release 2.

2. **Migrations rodando na primeira requisição HTTP** — achado já registrado em `memory/NEXT.md` desde a Release 3B (`boot()` aplica migrations, não há hook de inicialização de container). Com dois Engines no gateway, a primeira requisição fica mais pesada. Aceito conscientemente nesta Release; a correção (comando de migração explícito) é candidata natural à Release de CI/CD.

3. **Uma Mission criada não avança sozinha** — sem Planner, sem Agent, sem Skill, a Mission nasce e fica parada. Isso **não é um defeito**: é exatamente o estado esperado do sistema na Release 5.5, e precisa estar explícito no Validation Report para não ser lido como bug.

4. **Escopo pequeno demais para parecer útil** — dois endpoints não fazem um produto. O valor desta Release é de engenharia (provar a integração ponta a ponta), não de produto, e o Critério de Aceite reflete isso.

- `services/auth/bin/bootstrap-identity.php` + teste automatizado.
- `services/gateway` com as duas rotas, os dois Modules registrados e testes automatizados.

- **Decision Log** (`0005.5-vertical-slice-decision-log.md`).
- **Validation Report** (`0005.5-vertical-slice-validation-report.md`) — com a sequência `curl` completa e sua saída real, não parafraseada.
- `ROADMAP.md`/`memory/STATE.md`/`memory/NEXT.md` atualizados.

## Testes — três níveis ([ADR-0054](../adr/0054-tres-niveis-de-validacao.md))

**Automatizados** — testes das duas rotas novas em `services/gateway/tests/` (sucesso, token ausente, token inválido, Mission inexistente, corpo malformado) e do binário de bootstrap em `services/auth/tests/`. A suíte completa do monorepo permanece verde, sem regressão nos 246 testes atuais.

**Architecture Validation** — o gateway continua sem importar `Domain/` ou `Infrastructure/` de qualquer Engine diretamente (só `Interfaces/` e casos de uso resolvidos pelo container); nenhum Engine passa a depender de outro Engine; `composer.lock` do gateway não lista nada além do já previsto.

**Scenario Validation** — contra `docker compose up --build` real, a sequência completa:

```
bootstrap-identity.php  →  POST /auth/login  →  POST /auth/workspace
                        →  POST /missions    →  GET /missions/{id}
```

com a saída real de cada passo transcrita no Validation Report, mais os cenários de falha (sem token, token expirado, Plan vazio) e a confirmação de que os eventos de domínio de `MissionCreated` chegaram de fato ao Redis.

## Critérios de Aceite

1. Um usuário criado do zero pelo CLI consegue logar, selecionar Workspace, criar uma Mission e consultá-la — tudo por HTTP, contra o ambiente Docker real, com a saída transcrita no Validation Report.
2. A Mission criada está de fato persistida no MariaDB (verificável por consulta direta) e o evento `MissionCreated` foi de fato publicado no Redis.
3. `docker compose up` sobe o ambiente completo com `restart: on-failure` ativo, e `memory-worker` volta sozinho após um `docker stop redis && docker start redis` — o achado da 4.5 verificado como resolvido, não apenas alterado no arquivo.
4. Suíte completa do monorepo verde, sem regressão.
5. Decision Log e Validation Report publicados — sem os dois, a Release não está concluída.
