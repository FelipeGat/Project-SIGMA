# Release 5.5 — Vertical Slice — Decision Log

Decisões locais tomadas durante a Implementation, dentro do escopo já aprovado na [Proposal 5.5](0005.5-vertical-slice.md) — ver [ADR-0047](../adr/0047-decision-log-por-release.md). Onde uma decisão daqui acabar afetando outro módulo ou mudando um contrato, ela é promovida a ADR; nenhuma desta rodada chegou a esse ponto, mas duas chegaram perto e estão sinalizadas como candidatas.

## Achados reais (não previstos na Proposal)

### 1. O Identity Engine não sabia criar o Tenant que ele mesmo exige

`RegisterIdentity` existe desde a Release 3B e valida que o Tenant exista antes de criar um User. Mas **nenhum caminho de produção criava Tenant, Company ou Workspace** — `grep "new Tenant("` encontrava apenas fixtures de teste e a hidratação em `PdoTenantRepository`. Na prática, o Identity Engine estava completo para autenticar usuários que só podiam existir se alguém rodasse `INSERT` na mão.

Isso não aparecia como falha porque cada Release anterior montava sua própria hierarquia em `setUp()`. Só ficou visível ao tentar operar o sistema de fora.

**Decisão**: três casos de uso novos em `packages/identity-engine/src/Application/UseCase/` — `CreateTenant`, `CreateCompany`, `CreateWorkspace` — em vez de expor os repositórios no container. Os três Engines do projeto bindam **apenas casos de uso**, nunca repositórios (`IdentityEngineModule`, `MemoryEngineModule`, `MissionEngineModule` são unânimes nisso), e quebrar esse padrão para economizar três arquivos teria custado a consistência que ele garante.

**Nenhum dos três publica evento de domínio.** `Tenant`/`Company`/`Workspace` não são aggregates com eventos próprios no modelo atual, e inventar um `tenant.created` aqui exigiria catalogá-lo em `EVENT_CATALOG.md`/`contracts/Identity.contract.yaml` — decisão de modelagem que uma Release de vertical slice não deve tomar de passagem. Sinalizado como pendência.

### 2. O gateway com banco fora do ar deixava de responder `/health/live`

Ao registrar `identity-engine`/`mission-engine`, o gateway ganhou dependência de MariaDB pela primeira vez. `IdentityEngineModule::register()` lança `SigmaException` quando o banco está inalcançável (comportamento correto, introduzido na 3B), e `public/index.php` respondia 503 a **tudo** quando o boot falhava — inclusive `/health/live`.

Isso foi verificado de fato, não deduzido:

```
Bootstrap::fromManifestFile(..., DB_PORT=9999)
→ SigmaException: Module "identity-engine": não foi possível conectar ao banco
```

O comportamento era inofensivo enquanto uma falha de boot significava "configuração quebrada". Com dependência de infraestrutura externa, passou a significar "o banco piscou" — e aí viola [BOOTSTRAP.md § Health](../../BOOTSTRAP.md) diretamente: `/health/live` é o que o orquestrador usa para decidir se **reinicia o processo**; `/health/ready` é o que decide se ele **recebe tráfego**. Um MariaDB fora do ar é exatamente `not_ready`, nunca `unresponsive`. Mantido como estava, o Kubernetes/Docker entraria em restart-loop de um processo saudável, justamente quando a infraestrutura já está sob estresse.

**Decisão**: `services/gateway/src/BootFailureEndpoints.php` — com o boot falho, `/health/live` responde `200`, e apenas `ready`/`startup` e as rotas de domínio reportam `503`. Verificado no ambiente Docker real parando o container `mariadb`.

Isto corrige, na prática, a mitigação otimista que a própria Proposal escreveu no Risco 1: o `degraded` granular por Module **não** cobria este caso, porque a falha acontece em `register()`, antes de qualquer Module chegar a reportar estado ao `HealthManager`.

**Candidata a ADR**: se o mesmo padrão for necessário em `services/auth` (que tem exatamente o mesmo problema desde a 3B, ainda não corrigido), a política "falha de boot por dependência externa nunca é falha de liveness" deixa de ser local do gateway e vira decisão de arquitetura.

## Decisões de escopo

### `tenantId`/`workspaceId` vêm da Session, nunca do corpo da requisição

`POST /missions` resolve os dois via `ResolveContext`. O corpo da requisição é ignorado se trouxer esses campos — há teste automatizado provando isso (`test_tenant_and_workspace_come_from_the_session_not_from_the_body`) e validação real com dois Tenants distintos. Sem isso, qualquer requisitante autenticado criaria Mission no escopo de outro Tenant apenas mudando o JSON enviado, o que anularia [MULTITENANCY.md](../../MULTITENANCY.md) na primeira rota de domínio do projeto.

### Mission de outro Tenant responde `404`, não `403`

A existência de uma Mission é, ela mesma, informação do Tenant dono dela. Um `403` confirmaria a um estranho que aquele ID existe. Validado com dois Tenants reais: o mesmo token que recebe `201` criando Mission própria recebe `404` na Mission alheia, enquanto o dono recebe `200`.

### `intentId` é `null`, não um ID inventado

Sem Intent Engine (Release 7), nenhuma Mission criada por esta rota nasce de uma Intent registrada. `null` é o valor honesto.

### `PlanSource::Manual` e o Plan vindo no corpo

Não é contorno: [ADR-0092](../adr/0092-plan-e-conceito-proprio-do-mission-engine.md) determina que o Plan é **entrada** do Mission Engine, nunca produzido por ele, e `Plan.php` já documentava `Manual` como o único valor possível enquanto o Planner Engine não existir. Esta rota implementa literalmente o contrato existente.

### CLI, não endpoint HTTP, para o bootstrap de Identity

Mantido como proposto. Quem pode se registrar, sob qual convite e com qual verificação é decisão de produto sem contexto para ser tomada aqui. `IdentityBootstrapper` (em `src/`) carrega a lógica e é testável; `bin/bootstrap-identity.php` é só o invólucro CLI — mesma separação de `AuthEndpoints` em relação a `public/index.php`.

### O front controller continua sem framework

Cinco rotas ainda não justificam Laravel (mesma avaliação do [Decision Log da Release 2](0002-sigma-bootstrap-decision-log.md)). `GET /missions/{id}` é a primeira rota do projeto com segmento variável, resolvida com um `preg_match` antes do `match(true)` — explicitamente comentado no código como o ponto onde um roteador de verdade passa a fazer falta.

### Gateway e auth compartilham a mesma MariaDB

Schemas novos no banco já existente (`sigma_identity`), não banco nem container novo — mesma decisão já tomada na 4B para o Memory Engine. Confirmado no ambiente real: as seis tabelas do Mission Engine convivem com as do Identity Engine no mesmo schema.

## O que deliberadamente não foi feito

- **Os outros treze casos de uso do Mission Engine** continuam sem rota HTTP. Uma Mission criada por esta Release nasce `created` e **fica parada** — não há Planner, Agent ou Skill para fazê-la avançar. Isso não é defeito: é o estado esperado do sistema na Release 5.5, e está registrado no Validation Report para não ser lido como bug depois.
- **`services/auth` não ganhou o mesmo tratamento de boot degradado** que o gateway, apesar de ter o mesmo problema desde a 3B. Fora do escopo aprovado; ver Pendências do Validation Report.
- **Nenhuma `apps/*`**, nenhum framework HTTP, nenhuma migração de Redis pub/sub para Streams.
