# Release 5.6 — Observability Baseline — Decision Log

Decisões locais tomadas durante a Implementation, dentro do escopo aprovado na [Proposal 5.6](0005.6-observability-baseline.md) e da decisão de [ADR-0094](../adr/0094-health-endpoints-pertencem-ao-kernel.md) — ver [ADR-0047](../adr/0047-decision-log-por-release.md).

## Uma entrega da Proposal não existia

**A entrega 4 — "`depends_on` passa a usar `service_healthy` onde hoje usa a dependência simples" — era baseada em premissa errada.** Todos os `depends_on` do `docker-compose.yml` já usavam `condition: service_healthy` desde a Release 3B; não havia nenhuma dependência simples para converter. Verificado antes de tocar no arquivo.

Registrado aqui em vez de produzir trabalho inventado para preencher o item. As outras três entregas cobrem o objetivo da Release integralmente — o que faltava para o `depends_on` ter efeito real não era a condição, e sim os healthchecks que só agora existem: até esta Release, `condition: service_healthy` só podia se apoiar em `redis`/`mariadb`, porque nenhum serviço do SIGMA declarava saúde.

## `gateway.unavailable` virou `service.unavailable`

`BootFailureEndpoints::unavailable()` devolvia o código de erro `gateway.unavailable`. Ao subir a classe para o Kernel, esse código passaria a ser retornado também por `services/auth` — e por todo service futuro — nomeando um serviço que não é o que está respondendo.

**Decisão**: `service.unavailable`, com a mensagem correspondente generalizada. Mudança de contrato de resposta, mas de um código introduzido na Release 5.5, ainda sem nenhum consumidor externo.

## O teste de boot falho se dividiu em dois

`BootFailureEndpointsTest` (Release 5.5) misturava duas coisas: o *comportamento* das respostas no estado de boot falho, e a *causa* real (MariaDB inalcançável derrubando `IdentityEngineModule::register()`). A segunda parte não pode viver no Kernel — ele não conhece Engine nem service ([ADR-0040](../adr/0040-bootstrap-nao-conhece-engines.md)), e o teste importava `Sigma\Gateway\Bootstrap`.

**Decisão**: o comportamento fica em `packages/kernel/tests/Http/BootFailureEndpointsTest.php` (3 testes, sem dependência de Engine); a causa vira `services/gateway/tests/BootFailsWithUnreachableDatabaseTest.php`, e a mesma prova é replicada em `services/auth/tests/HealthRoutesTest.php`, já que agora os dois services enfrentam a situação. Cada arquivo aponta para o outro no docblock.

## `/health/ready` como alvo do healthcheck, não `/health/live`

O `healthcheck` do Docker responde "este container deve receber tráfego?" — que é literalmente o que `ready` significa em [ADR-0042](../adr/0042-health-estilo-kubernetes.md). Apontá-lo para `live` tornaria o healthcheck inútil: `live` responde `200` justamente nos casos em que o serviço **não** deve receber tráfego (boot falho por banco fora do ar).

Consequência desejada e verificada: um Module `degraded` tira o serviço do tráfego **sem** que o processo precise morrer, que era a intenção original de [ADR-0041](../adr/0041-lifecycle-estendido.md) e nunca havia se concretizado.

## `start_period: 30s`

As migrations do Identity e do Mission Engine rodam na primeira requisição HTTP (pendência aberta desde a Release 3B), então a primeira resposta é mais lenta que as seguintes. Sem folga, o container seria marcado `unhealthy` durante uma subida perfeitamente normal — o Risco 2 da Proposal.

Na prática o ambiente ficou `healthy` em **menos de 5s**, bem dentro da folga. Os 30s permanecem por margem: o valor foi calibrado para o pior caso (primeira subida, banco vazio, migrations completas), não para o caso medido numa máquina com cache quente.

## `curl`, não `wget`, no healthcheck

Ambos existem nas imagens (`php:8.2-cli-alpine` + o `curl` que o próprio Dockerfile instala para baixar o Composer) — confirmado com `command -v` dentro do container em execução, não presumido. `curl -fsS` foi escolhido por `-f` fazer o exit code refletir o status HTTP, que é exatamente a semântica que o healthcheck precisa.

## `memory-worker` sem healthcheck

Exceção explícita já registrada em ADR-0094: não há endpoint a consultar num processo que nunca escuta HTTP (decisão da Release 4B). Sua saúde continua sendo "o processo está vivo", coberta por `restart: on-failure`. O comentário no `docker-compose.yml` diz isso, para que a ausência não seja lida como esquecimento.

## O que não foi feito

- **Nenhum dos outros três pilares de [TELEMETRY.md](../../TELEMETRY.md)** (Metrics, Tracing, Audit) — fora do escopo, Release 23.
- **`/health/details`** continua no backlog de `memory/NEXT.md`.
- **Reconexão automática ao banco dentro do processo** — um Module que falhou no boot continua exigindo restart. O que mudou é que agora o orquestrador **sabe**. A estratégia de reconexão robusta segue como pendência desde a 4B.
