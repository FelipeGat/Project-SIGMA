# Release 3.5 — Architecture Consolidation

Proposta formal, no formato exigido por [ADR-0010](../adr/0010-processo-por-epicos-com-aprovacao.md), seguindo o processo de quatro fases de [ADR-0048](../adr/0048-processo-quatro-fases.md). **Revisão 1 — aprovada, implementação autorizada** (decisão do Product Owner na mesma mensagem que a propôs, ver `memory/DECISIONS.md`).

Diferente de toda Release anterior, esta **não muda o produto** — não adiciona nenhuma Capability, endpoint ou entidade nova. É uma Release de fortalecimento de base, inserida deliberadamente entre a Release 3 (Identity Engine, completa) e a Release 4 (Memory Engine, ainda não iniciada): "É muito mais barato consolidar agora do que corrigir depois da Mission, Planner e Agent."

## Objetivo

Consolidar o que já existe antes de crescer mais: nomear e catalogar formalmente o que hoje só existe implícito no código (eventos, versão por Engine), auditar a aderência do código real às ADRs/Contracts/Decision Logs já escritos, medir a distribuição de testes por camada, e provar — em ambiente limpo, não reaproveitando estado de sessões anteriores — que o fluxo fim-a-fim (`bootstrap → login → workspace → logout`) continua funcionando exatamente como validado na Release 3B.

## Escopo

**Existe:**
- `EVENT_CATALOG.md` — catálogo de todo evento de domínio do SIGMA (hoje só Identity Engine), com colunas que `DOMAIN_EVENTS.md` ainda não tinha: quem pode consumir, versão, contrato.
- `packages/identity-engine/VERSION.md` — primeiro Engine a formalizar versão própria (Semantic Versioning por Engine, não só por projeto).
- `CHANGELOG.md` (raiz) — histórico voltado a quem vai usar o SIGMA, não a quem o desenvolve; retroativo às Releases 0–3.
- Renomeação de `PasswordHasher` para `CredentialProvider` em `packages/identity-engine` — **sem mudar comportamento nenhum**, mesmos métodos, mesma implementação Argon2id por trás, só o nome deixa de presumir "senha" como único mecanismo de credencial (prepara Passkey/OAuth/biometria, sem implementá-los agora).
- Validação cruzada: cada `contracts/*.contract.yaml` comparado com o código real que ele descreve; cada ADR citada em código/documentação verificada como existente e consistente; cada Decision Log revisado quanto a pendências ainda não resolvidas.
- Revisão de testes por camada — contagem e distribuição (Domain/Application/Infrastructure/Interfaces) por pacote, coverage de código se a ferramenta estiver disponível no ambiente.
- Repetição do teste `bootstrap → login → workspace → logout`, desta vez em ambiente Docker genuinamente limpo (`docker compose down -v` antes de `up --build`, sem estado residente de validações anteriores).
- ADRs formalizando duas confirmações (já satisfeitas pelo código existente, sem mudança necessária) e duas direções aprovadas para quando Identity/Session forem tocados de novo com mudança de comportamento real (fora do escopo desta Release, mas registradas para não se perderem).

**Não existe:** nenhuma Capability nova, nenhuma mudança de schema, nenhuma mudança de comportamento em `Domain/`/`Application/` além da renomeação mecânica de `PasswordHasher`. Especificamente fora de escopo (viram ADR de direção, não implementação): `Workspace`/`Context` migrarem conceitualmente de `Identity` para `Session`; metadata padrão em todo evento de domínio (`causationId`, `actor`, `workspace`).

## Arquitetura

Nenhuma mudança arquitetural nesta Release — é sobre tornar explícito o que a arquitetura das Releases 0–3 já estabeleceu, e verificar que o código bate com o que está documentado. `EVENT_CATALOG.md` e `VERSION.md` seguem o mesmo padrão de documento-antes-do-código já usado desde a Release 3 (`IDENTITY_MODEL.md`, `IDENTITY_LIFECYCLE.md`, `DOMAIN_EVENTS.md`) — a diferença é que aqui o código já existe, o documento é que estava faltando.

## Dependências

- Release 3 (3A + 3B) — implementada, validada, aprovada.

## Riscos

1. **Renomear `PasswordHasher` sem quebrar nada** — mitigado pela suíte de testes já existente (135 testes cobrindo exatamente os pontos que usam essa interface); qualquer regressão aparece imediatamente.
2. **"Validação cruzada" pode virar um exercício infinito** dado o tamanho já grande da documentação — mitigado por escopo fechado: só o que já existe em código (Contracts, ADRs citadas, Decision Logs), não uma auditoria de toda a documentação de visão/produto.
3. **Ambiente limpo pode revelar que a Release 3B só funcionou por causa de estado residente** — esse é exatamente o propósito do teste; se acontecer, é um achado real desta Release, documentado, não escondido.

## Entregáveis

- `EVENT_CATALOG.md`, `packages/identity-engine/VERSION.md`, `CHANGELOG.md`.
- `PasswordHasher` renomeado para `CredentialProvider` em todo o código e testes que o referenciam.
- Relatório de validação cruzada (Contracts/ADRs/Decision Logs) — dentro do próprio Decision Log desta Release.
- Relatório de testes por camada — dentro do Validation Report desta Release.
- **Decision Log** (`docs/releases/0003.5-architecture-consolidation-decision-log.md`).
- **Validation Report** (`docs/releases/0003.5-architecture-consolidation-validation-report.md`).

## Testes — três níveis ([ADR-0054](../adr/0054-tres-niveis-de-validacao.md))

### 1. Testes Automatizados
- Suíte completa do monorepo (135 testes) continua 100% verde após a renomeação de `CredentialProvider`.

### 2. Architecture Validation
- Todo `contracts/*.contract.yaml` corresponde à interface/classe real que descreve — nenhuma divergência de campo ou assinatura.
- Toda ADR referenciada em comentário de código ou em outra ADR existe de fato em `docs/adr/`.

### 3. Scenario Validation
- `docker compose down -v` (remove volumes, força estado limpo) seguido de `docker compose up --build` — fluxo `login → workspace → context → logout` validado via HTTP real, do zero, sem reaproveitar nenhum dado seedado em rodadas anteriores.

## Critérios de Aceite

- Os três documentos novos existem e estão corretos.
- `CredentialProvider` substitui `PasswordHasher` em 100% do código, suíte continua verde.
- Relatório de validação cruzada publicado, com toda divergência encontrada listada explicitamente (mesmo que pequena) — nunca "nada encontrado" sem evidência do que foi checado.
- Fluxo completo validado em ambiente Docker limpo, do zero.
