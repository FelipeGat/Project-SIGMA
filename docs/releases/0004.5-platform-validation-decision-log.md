# Release 4.5 — Platform Validation — Decision Log

Decisões locais e achados durante a execução, dentro do escopo já aprovado em [0004.5-platform-validation.md](0004.5-platform-validation.md) (revisão 1). Ver [ADR-0047](../adr/0047-decision-log-por-release.md) para o que este documento é (e não é).

## O que foi executado

As dez verificações do Escopo, todas contra o `docker compose up --build` real (não um ambiente sintético) — `redis`, `mariadb`, `gateway`, `auth`, `memory-worker`. Ver [Validation Report](0004.5-platform-validation-validation-report.md) para os números completos.

## O achado mais importante: nenhum serviço tem `restart policy` no `docker-compose.yml`

**Não estava listado nos dez itens originais, mas apareceu organicamente ao executar o item 2 (restart de containers) em sequência com o item 3 (perda do Redis).** `docker/docker-compose.yml` não declara `restart:` em nenhum serviço — nem `on-failure`, nem `unless-stopped`. Na prática, isso significa: se `memory-worker` cair por qualquer motivo (e ele cai — ver achado abaixo), **ninguém o reinicia sozinho**. Um operador humano (ou uma orquestração externa como Kubernetes, fora do escopo desta Release) precisa notar a queda e agir.

Diferente dos achados de "perda de mensagem" (esperados desde a Proposal), este não foi antecipado — é genuinamente novo, encontrado só ao testar a sequência real de falhas, não a arquitetura em teoria. Sinalizado como Pendência de alta prioridade, **não corrigido nesta Release** (mudaria `docker-compose.yml`, fora do escopo "nenhuma mudança de comportamento" desta Proposal) — mas é o tipo de achado que a própria Release 4.5 existe para revelar.

## Achado confirmado (esperado desde a Proposal): `memory-worker` morre com qualquer interrupção da conexão Redis, não só timeout de inatividade

A Release 4B já havia corrigido o timeout por inatividade (`read_write_timeout: -1`, ver Decision Log da 4B). Esta Release revela que essa correção **não cobre uma interrupção real da conexão** — quando o processo `redis` é reiniciado (ou parado), a conexão TCP que `RedisSubscriber::listen()` mantém aberta em `pubSubLoop()` é derrubada de verdade, e não há nenhum `try`/`catch`/retry ao redor do loop bloqueante em `bin/worker.php`. O processo morre com `Predis\Connection\ConnectionException` não tratada. Combinado com a ausência de `restart policy` (achado acima), isso significa: **qualquer interrupção momentânea do Redis, mesmo um restart de rotina, exige intervenção manual para o Memory Engine voltar a sincronizar `UserTwin`**.

`services/auth`/`services/gateway`, em contraste, **sobrevivem sozinhos** a uma queda do Redis — não mantêm uma conexão bloqueante aberta, então uma falha de publish vira um `500` tratado (`auth.internal_error`, já corrigido na Release 3B) em vez de derrubar o processo; voltam a funcionar normalmente assim que o Redis volta, sem reinício manual.

## Achado confirmado (esperado desde a Proposal): mensagem publicada durante a queda do Worker é perdida para sempre

Provado com evidência concreta, não só teoricamente: um usuário real (via `services/auth`, fluxo HTTP completo) selecionou um Workspace novo enquanto `memory-worker` estava fora do ar — a chamada HTTP teve sucesso (`200`, o Redis aceitou o `PUBLISH` mesmo sem nenhum assinante ativo), mas depois que o `memory-worker` foi religado, o `UserTwin` correspondente **continuou mostrando o Workspace anterior**, nunca o novo. A mensagem não foi enfileirada em lugar nenhum — Redis pub/sub não persiste para assinante ausente, ao contrário de Redis Streams (que usa `XADD`/consumer groups com histórico).

Isso responde também o item 9 (Event Replay) diretamente: **não existe nenhum mecanismo de reprocessar um evento perdido** — nem no `RedisSubscriber`, nem em lugar nenhum do projeto. Confirma a expectativa já registrada na Proposal.

## Recomendação (não implementada nesta Release)

Duas mudanças resolveriam os dois achados acima, mas nenhuma foi implementada aqui — por decisão explícita da própria Proposal ("nenhuma mudança de comportamento... a correção vira uma ADR de direção e uma Proposal própria"):

1. **`restart: on-failure` (ou `unless-stopped`) em todos os serviços do `docker-compose.yml`** — mudança pequena, baixo risco, resolveria pelo menos a recuperação automática do container (ainda não a perda de mensagem em si).
2. **Migrar de Redis pub/sub para Redis Streams** (`XADD`/`XREADGROUP`, consumer groups com `XACK`) — mudança maior, dá persistência real e replay a eventos não processados; candidata natural para quando o componente estrutural **Scheduler** ou a Release 23 (Production Hardening) forem desenhados em detalhe. Fica sinalizada em `memory/NEXT.md`, não decidida aqui.

## O que funcionou bem, com evidência

- **Stress test de 1000 eventos**: 0 eventos perdidos quando o `memory-worker` está de pé — o gargalo é processamento sequencial (~112 eventos/s), não perda.
- **Latência**: p50 ~6ms, p95 ~12ms, p99 ~23ms — publish→persistência, com o worker de pé. Excelente para o volume esperado antes da Mission Engine existir.
- **Múltiplos usuários concorrentes (20)**: 0 falhas de login, 0 falhas/mismatches de seleção de Workspace, 0 contaminação cruzada entre `UserTwin`s — a Application/Infrastructure do Memory Engine se comporta corretamente sob concorrência real.
- **Memory Promotion em volume (200 registros, 20 subjects × 5 Workspaces × 2 Missions)**: contagem de promoções a Project e a LongTerm bateu exatamente com o esperado — os dois gates (estrutura + `confidence`) continuam corretos fora dos testes unitários de 4A/4B.
- **Twin Sync sequencial (4 trocas de Workspace)**: o estado final sempre reflete a última troca, mesmo com múltiplos eventos em sequência rápida para a mesma identidade.
- **Recuperação do `auth`/`gateway` após perda do Redis**: automática, sem intervenção — nenhuma mudança necessária.
