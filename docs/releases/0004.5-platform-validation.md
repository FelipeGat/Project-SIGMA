# Release 4.5 — Platform Validation

Proposta formal, no formato exigido por [ADR-0010](../adr/0010-processo-por-epicos-com-aprovacao.md), seguindo o processo de quatro fases de [ADR-0048](../adr/0048-processo-quatro-fases.md). **Revisão 1 — aguardando aprovação do Product Owner.** Marco de engenharia acrescentado pelo Product Owner ao roadmap em 2026-08-04, entre a Release 4 (Memory Engine, completa) e a Release 5 (Mission Engine): "provar que tudo que construímos até hoje funciona junto" — antes de a Mission Engine passar a depender de Identity, Memory, Redis, Docker, Gateway e Worker todos operando corretamente sob condições reais, não só isoladamente Release a Release.

Diferente de toda Release anterior, **não muda o produto** — não adiciona nenhuma Capability, endpoint ou entidade nova. Mesmo espírito da Release 3.5 (Architecture Consolidation), mas com um objetivo diferente: 3.5 auditou coerência entre documentação e código; 4.5 audita **comportamento sob estresse e sob falha** do sistema já construído.

## Objetivo

Medir e documentar como o SIGMA se comporta sob dez condições reais — volume, reinício, perda parcial de infraestrutura, concorrência, e o ciclo completo de Memory — usando o próprio ambiente Docker já validado nas Releases 3B/4B, não um ambiente sintético separado. Onde o comportamento for bom, documentar a evidência; onde revelar uma limitação real (esperado, dado que `RedisSubscriber` usa Redis pub/sub, não Streams — sem persistência de mensagem), documentar a limitação explicitamente como Pendência, nunca maquiada como sucesso.

## Escopo

**Existe** — dez verificações, cada uma com critério de sucesso e evidência exigida:

1. **Stress test — 1000 eventos**: publicar 1000 eventos `identity.created`/`workspace.selected` sintéticos através do Redis real e confirmar que `memory-worker` processa todos, medindo taxa de processamento (eventos/segundo) e uso de memória do worker antes/depois.
2. **Restart de containers — recuperação**: reiniciar cada container (`auth`, `gateway`, `memory-worker`, `mariadb`, `redis`) individualmente e em conjunto; confirmar que os health checks voltam a `healthy` e que dados já persistidos (Identity, `UserTwin`) sobrevivem.
3. **Perda do Redis — recuperação**: parar o container `redis` com `auth`/`memory-worker` já rodando; observar o comportamento de cada um (esperado: `auth` falha novas publicações mas não derruba o processo HTTP; `memory-worker` cai, já que depende de uma conexão Redis ativa para o loop bloqueante); religar o Redis e confirmar se cada processo se recupera sozinho ou exige restart manual — documentar qual dos dois, sem presumir.
4. **Perda do Worker — recuperação**: parar `memory-worker`, publicar eventos reais (login/workspace) enquanto ele está fora, religar o worker; confirmar **quais eventos publicados durante a queda são perdidos** — esperado, dado que Redis pub/sub (usado por `RedisSubscriber`) não persiste mensagens para assinantes ausentes, ao contrário de Redis Streams. Este é o resultado mais provável de todo o escopo: **não** uma falha da Implementation, e sim uma característica arquitetural da Release 4B que só fica visível testando de propósito — documentar como achado real, não escondido.
5. **Múltiplos usuários concorrentes**: N registros/logins simultâneos (via múltiplos processos PHP ou requisições paralelas), confirmar isolamento correto por `tenantId`/`identityId` — nenhum `UserTwin` de um usuário contaminado pelo de outro.
6. **Ciclo completo de Memory Promotion sob dados reais**: várias Missions/Workspaces reais via os casos de uso já implementados (`EvaluateMemoryPromotion`) contra MariaDB real, confirmando que os dois gates (estrutura + `confidence`) continuam corretos em volume, não só nos testes unitários já existentes.
7. **Twin Sync ampliado**: múltiplos usuários, múltiplas trocas de Workspace ao longo do tempo — confirmar que `UserTwin.state` sempre reflete o último evento processado, mesmo com vários eventos em sequência rápida para o mesmo usuário.
8. **Latência**: medir o tempo entre a publicação de um evento (`auth`) e sua persistência efetiva (`memory-worker` → MariaDB) — p50/p95/p99 sobre uma amostra razoável (ex: 100-500 eventos).
9. **Event Replay**: verificar se existe algum mecanismo de reprocessar eventos já publicados (ex: para recuperar do item 4). Esperado: **não existe** — Redis pub/sub não guarda histórico, `RedisSubscriber` não implementa nenhum buffer próprio. Documentar isso como limitação conhecida, não como algo a implementar nesta Release (migrar para Redis Streams é escopo maior, candidato a ADR de direção para uma Release futura de hardening).
10. **Benchmark de referência**: consolidar os números dos itens 1/8 num documento de referência (`docs/releases/0004.5-platform-validation-benchmark.md` ou seção própria do Validation Report) — números concretos, ambiente descrito, reproduzível.

**Não existe**: nenhuma mudança de comportamento em `Domain/`/`Application/` de nenhum Engine. Se os itens 4/9 revelarem que perda de mensagem é inaceitável para o projeto, a correção (ex: migrar para Redis Streams) vira uma ADR de direção e uma Proposal própria — não implementada silenciosamente dentro desta Release de validação.

## Arquitetura

Nenhuma mudança arquitetural — esta Release observa e mede o que já existe. As dez verificações rodam contra o `docker-compose.yml` já existente (Releases 3B/4B), com scripts de apoio (geração de eventos sintéticos, medição de latência) escritos como ferramentas descartáveis em `tools/` ou no scratchpad da sessão, não como código de produção de nenhum Engine.

## Dependências

- Release 4 (4A + 4B) — implementada, validada, aprovada.
- Docker Desktop disponível (já confirmado nesta sessão).

## Riscos

1. **Itens 4 e 9 provavelmente revelam uma limitação real de perda de mensagem** — não é um risco a mitigar, é o próprio objetivo da verificação; o risco real é documentar isso de forma incompleta ou otimista demais.
2. **1000 eventos sintéticos podem não representar o padrão de tráfego real** (Mission Engine, quando existir, terá um perfil de evento diferente) — aceito conscientemente; o objetivo é validar que a arquitetura atual não quebra sob volume, não prever o volume exato de produção.
3. **Testar perda de containers em ambiente de desenvolvimento local pode ser instável** (Docker Desktop no Windows) — mitigado por documentar exatamente o comando usado e o resultado obtido, sem re-executar até "dar certo".

## Entregáveis

- **Decision Log** (`docs/releases/0004.5-platform-validation-decision-log.md`) — o que foi encontrado e por quê, incluindo qualquer limitação real revelada.
- **Validation Report** (`docs/releases/0004.5-platform-validation-validation-report.md`) — os dez itens, cada um com evidência concreta (comando, número, log), nunca "✅ funciona" sem prova.
- Eventuais ADRs de direção para limitações encontradas que exijam decisão futura (ex: Redis Streams vs. pub/sub) — sinalizadas, não implementadas nesta Release.

## Testes — três níveis ([ADR-0054](../adr/0054-tres-niveis-de-validacao.md))

Esta Release **é**, ela mesma, essencialmente Scenario Validation — os dez itens do Escopo substituem a separação usual em Testes Automatizados/Architecture Validation/Scenario Validation, já que não há código de domínio novo para testar em unidade. Architecture Validation permanece implícita: nenhuma mudança de código de produção nesta Release para validar.

## Critérios de Aceite

- Os dez itens do Escopo executados de fato, cada um com evidência concreta no Validation Report — nenhum pulado silenciosamente.
- Toda limitação real encontrada (esperada nos itens 4/9) documentada explicitamente, com uma recomendação clara sobre se/quando endereçar (ADR de direção, ou aceito conscientemente).
- Suíte automatizada dos oito pacotes/serviços existentes continua 100% verde ao final (nenhuma regressão introduzida pelos scripts de validação).
