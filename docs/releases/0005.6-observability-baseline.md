# Release 5.6 — Observability Baseline

Proposta formal, no formato exigido por [ADR-0010](../adr/0010-processo-por-epicos-com-aprovacao.md), seguindo o processo de quatro fases de [ADR-0048](../adr/0048-processo-quatro-fases.md). **Revisão 1 — aguardando aprovação do Product Owner.**

Fecha o buraco que a [Release 5.5](0005.5-vertical-slice.md) abriu ao dar ao gateway sua primeira dependência de infraestrutura externa. Depende da aprovação conjunta de [ADR-0094](../adr/0094-health-endpoints-pertencem-ao-kernel.md), que é a decisão de arquitetura por trás dela.

## Objetivo

Fazer o SIGMA **reagir** ao próprio estado de saúde, em vez de apenas relatá-lo.

Os três endpoints de health existem desde a Release 2, respondem corretamente, reportam estado granular por Module — e **nada os consome**. Nenhum serviço do SIGMA tem `healthcheck` no `docker-compose.yml`; só `redis` e `mariadb`, que são imagens de terceiros. Na prática:

- Um `gateway` com o banco fora do ar continua recebendo tráfego.
- O `restart: on-failure` da Release 5.5 reage a um processo que *morre*, nunca a um que ficou `not_ready`.
- `services/auth` está no ar desde a Release 3B **sem nenhum endpoint de health** — um ponto cego operacional completo.
- A granularidade `degraded` por Module, desenhada em [ADR-0041](../adr/0041-lifecycle-estendido.md), não influencia nenhuma decisão real.

A ADR-0042 chegou a declarar, como consequência, que "o `docker-compose.yml` já aponta para estes três endpoints". Nunca apontou. Esta Release torna verdadeira uma afirmação que está no repositório desde a Release 2.

## Escopo

**Existe** — quatro entregas, nesta ordem:

1. **`HealthEndpoints` e `BootFailureEndpoints` migram para `packages/kernel`** (`Sigma\Kernel\Http\`), conforme ADR-0094. `services/gateway` passa a consumi-las em vez de possuí-las. Os testes existentes migram junto, adaptados aos novos namespaces.

2. **`services/auth` ganha os três endpoints** — `/health/live`, `/health/ready`, `/health/startup`, com o mesmo tratamento de boot degradado do gateway (`live` responde `200` mesmo com MariaDB fora do ar; `ready`/`startup` e as rotas `/auth/*` respondem `503`).

3. **`healthcheck` no `docker-compose.yml`** para `gateway` e `auth`, apontando para `/health/ready` — o endpoint que responde "devo receber tráfego". `memory-worker` fica de fora por não escutar HTTP (ADR-0094, exceção explícita); continua coberto por `restart: on-failure`.

4. **`depends_on` passa a usar `service_healthy`** onde hoje usa a dependência simples, de modo que um serviço só entre no ar quando aquilo de que depende estiver de fato pronto.

**Não existe** — explicitamente fora do escopo:

- **Métricas, tracing e audit.** [TELEMETRY.md](../../TELEMETRY.md) define quatro pilares; esta Release trata de health, que é o mínimo operacional, não de observabilidade completa. Prometheus/OpenTelemetry são escopo da Release 23 (Production Hardening).
- **`/health/details`** (`status`, `modules[]`, `version`, `uptime`) — está no backlog de `memory/NEXT.md` e continua lá.
- **Qualquer mudança em `Domain/`/`Application/` de qualquer Engine.** Nenhuma linha.
- **Reconexão automática ao banco/Redis dentro do processo.** Um Module que falhou no boot continua exigindo restart do processo; o que muda é que agora o orquestrador **sabe disso**. Estratégia de reconexão robusta permanece a pendência já sinalizada desde a 4B.
- **Novos endpoints de domínio.** As rotas de Mission da 5.5 permanecem as únicas.

## Arquitetura

`packages/kernel` ganha `src/Http/` com as duas classes. Elas dependem apenas de `HealthManager` (do próprio Kernel) e `Envelope` (de `packages/core`) — não conhecem SAPI, roteamento, middleware, nem qualquer conceito de domínio. [ADR-0040](../adr/0040-bootstrap-nao-conhece-engines.md) permanece intacta: o Kernel continua sem saber que Engine existe.

Cada front controller (`services/gateway/public/index.php`, `services/auth/public/index.php`) continua fazendo seu próprio roteamento com `match` — o Kernel oferece as respostas, nunca as rotas. Nenhum framework HTTP entra nesta Release.

`services/auth/composer.json` já depende de `sigma/kernel`; nenhuma dependência nova em nenhum pacote.

## Dependências

- **[ADR-0094](../adr/0094-health-endpoints-pertencem-ao-kernel.md) aprovada** — esta Release é a implementação daquela decisão.
- Release 5.5 completa (`BootFailureEndpoints` existe e está validada).

## Riscos

1. **Mover classes entre pacotes quebra imports.** Hoje só `services/gateway/public/index.php` e dois arquivos de teste importam `Sigma\Gateway\HealthEndpoints`. Risco baixo e totalmente contido; a suíte completa (265 testes) é a rede de segurança.

2. **`healthcheck` mal calibrado pode marcar um serviço saudável como `unhealthy`** — `start_period` curto demais é o erro clássico, já que as migrations do Identity/Mission Engine rodam na primeira requisição HTTP (pendência conhecida desde a 3B) e a primeira resposta é mais lenta. Mitigação: `start_period` folgado (30s) e validação real com `docker compose up --build`, observando a transição `starting → healthy` de fato, não presumindo-a.

3. **`depends_on: service_healthy` pode travar a subida do ambiente** se um healthcheck nunca passar. Mitigação: validar o ciclo completo (`up`, `stop mariadb`, `start mariadb`) antes de considerar a Release pronta, e documentar o tempo real de subida no Validation Report.

4. **O Kernel ganha uma pasta `Http/`, aproximando-o de um framework** — custo já discutido e aceito em ADR-0094, mitigado por escopo estrito.

## Entregáveis

- `packages/kernel/src/Http/HealthEndpoints.php` e `BootFailureEndpoints.php`, com seus testes.
- `services/auth` com os três endpoints, boot degradado e testes.
- `services/gateway` consumindo o Kernel em vez das próprias classes.
- `docker/docker-compose.yml` com `healthcheck` em `gateway`/`auth` e `depends_on: service_healthy`.
- **Decision Log** (`0005.6-observability-baseline-decision-log.md`).
- **Validation Report** (`0005.6-observability-baseline-validation-report.md`).
- `ROADMAP.md`/`CHANGELOG.md`/`memory/STATE.md`/`memory/NEXT.md` atualizados; ADR-0094 de `Proposto` para `Aceito`.

## Testes — três níveis ([ADR-0054](../adr/0054-tres-niveis-de-validacao.md))

**Automatizados** — os testes de `HealthEndpoints`/`BootFailureEndpoints` migram para `packages/kernel` e continuam verdes; `services/auth` ganha testes dos três endpoints (caminho normal e boot degradado), no mesmo formato dos do gateway. Os 265 testes atuais permanecem verdes, sem regressão.

**Architecture Validation** — `packages/kernel/src/Http/` não importa nada de nenhum Engine nem de `services/*`; nenhum `use Sigma\Gateway\HealthEndpoints` sobra no repositório; `composer.lock` de nenhum pacote ganha dependência nova.

**Scenario Validation** — contra `docker compose up --build` real:

1. `docker compose ps` mostra `gateway` e `auth` como `healthy` (não apenas `Up`) — a transição `starting → healthy` observada de fato.
2. `docker compose stop mariadb` → ambos passam a `unhealthy`, `/health/live` continua `200` em ambos, `/health/ready` responde `503`.
3. `docker compose start mariadb` → ambos voltam a `healthy` sozinhos, com o tempo real medido.
4. O caminho ponta a ponta da Release 5.5 (login → workspace → criar Mission → consultar) continua funcionando, sem regressão.

## Critérios de Aceite

1. `docker compose ps` reporta `gateway` e `auth` como `healthy`, usando os endpoints do SIGMA — não `Up` genérico.
2. Com o MariaDB fora do ar, ambos os serviços respondem `200` em `/health/live` e `503` em `/health/ready`, e ambos aparecem `unhealthy` para o orquestrador; ao religar, voltam sozinhos, com o tempo registrado.
3. Nenhum `Sigma\Gateway\HealthEndpoints` restante no repositório — a migração é completa, não uma cópia.
4. O caminho ponta a ponta da Release 5.5 continua funcionando.
5. Suíte completa verde, sem regressão.
6. Decision Log e Validation Report publicados; ADR-0094 marcada como `Aceito`.
